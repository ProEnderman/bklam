# Forecast-модуль: как устроен и что считает

## Назначение

Python-микросервис (FastAPI, порт 8090) для **прогнозирования метрик ресторана** на горизонт от 1 до 90 дней. Данные для обучения и фактов берутся **только из Java-бэкенда** по внутреннему API (JWT); прямого доступа к БД нет.

---

## Метрики

| Метрика        | Описание                    | Источник данных |
|----------------|-----------------------------|------------------|
| **revenue**    | Дневная выручка             | Java: заказы (total_amount), status=CLOSED |
| **bookings**   | Количество бронирований/позиций в день | Java: сумма `order_items.qty` по закрытым заказам |
| **avg_check**  | Средний чек (revenue / bookings) | Считается из revenue и bookings |
| **cancel_rate**| Доля отмен                   | Заглушка (нет реальных данных) |
| **utilization**| Загрузка (например, столов) | Заглушка (нет реальных данных) |

Реальные ряды для обучения и сравнения с прогнозом есть у **revenue**, **bookings** и **avg_check**. Остальные метрики считаются по заглушкам и не имеют реальной аналитики.

---

## Архитектура потока данных

1. **Запрос с фронта** → Java Backend (8080) → проверка прав, подпись внутренним JWT.
2. **Java** проксирует запрос в **Forecast Service** (8090) с заголовком `Authorization: Bearer <internal_jwt>`.
3. **Forecast Service** по JWT знает tenant_id (ресторан); при необходимости данных дергает Java:  
   `GET /api/internal/forecast-data/orders?from=...&to=...` с тем же токеном.
4. Ответ (даты, выручка, количество позиций) превращается в дневные ряды (revenue/bookings), по ним обучаются модели и строятся прогнозы.

Спеки моделей и прогнозы хранятся **по ресторанам**: для каждого `restaurant_id` (tenant_id) своя директория `specs/<tenant_id>/` (и `specs/<tenant_id>/monthly/` для месячных срезов). При первом и еженедельном запуске для ресторана записывается прогноз на 30 дней вперёд; при еженедельном запуске по понедельникам в 03:00 прогноз пересчитывается (актуальные 30 дней с учётом новых данных).

## Что считает модуль (по шагам)

### 1. Обучение и выбор модели (train)

- **Эндпоинт:** `POST /api/forecast/train/{metric}` (и опционально `train/all`).
- Загружается история метрики через `load_metric` → для revenue/bookings это вызов Java `/forecast-data/orders` и преобразование в дневные ряды.
- **Селектор** перебирает кандидатов:
  - **Базовые:** скользящее среднее (MA7), same-day-last-week.
  - **SARIMA** — перебор порядков/сезонности, бэктест по фолдам.
  - **Prophet** — с опцией праздников/событий.
  - **SARIMAX с экзогенными переменными** — праздники, базовая серия и т.д.
  - **Two-stage** — факторизация: прогноз bookings + avg_check → revenue (при достаточной истории).
  - **Ensemble** — взвешенное усреднение SARIMA, Prophet, SARIMAX-exog по бэктесту.
- По бэктесту выбирается модель с лучшей метрикой (MAPE/SMAPE/MAE в зависимости от метрики), результат сохраняется в `specs/{metric}.json` (имя модели, параметры, `trained_at`). Повторное обучение не чаще чем раз в `RETRAIN_INTERVAL_DAYS` (7), если не передан `force=true`.

### 2. Прогноз на горизонт (forecast)

- **Эндпоинты:** `GET /api/forecast/summary` (все метрики) и `GET /api/forecast/{metric}?horizon=...`.
- Загружается спека и история. Если спеки нет — сначала вызывается обучение.
- По выбранной модели (sarima, prophet, sarimax_exog, two_stage, ensemble, ma7, same_day_last_week) строится прогноз на `horizon` дней **от последней даты в истории**.
- Выход: даты, точечный прогноз (`yhat`), нижняя/верхняя границы, имя модели, тренд (up/down/stable), MAPE по бэктесту. Результат сохраняется в `specs/{metric}_forecast.json` (этот файл используется для «последнего прогноза» и месячных срезов).
- Для revenue/bookings при `hierarchical=true` возможен иерархический прогноз (по сегментам; сегменты пока без реальных данных).

### 3. Прогноз на календарный месяц (monthly)

- **Эндпоинт:** `GET /api/forecast/{metric}?period=month&year=...&month=...`.
- Берётся последний сохранённый дневной прогноз (`load_latest_forecast`) и факты за месяц из Java (`load_daily_actuals_for_month`).
- **Агрегация** (`build_full_month_snapshot`): по каждому дню месяца подставляется либо факт (если есть), либо значение из дневного прогноза; пропуски заполняются по «ближайшему соседу». Итог по месяцу:
  - для revenue/bookings — сумма по дням;
  - для avg_check — среднее по дням (с учётом bookings для взвешивания).
- Результат кэшируется в `specs/monthly/{metric}_{year}_{month}.json`: `predicted_total`, доверительный интервал, покрытие (сколько дней факт/прогноз), модель.

Важно: дневной прогноз в файле имеет ограниченный горизонт (например, 14 дней от конца истории). Если в этом прогнозе нет дат выбранного месяца, месячный срез собирается из фактических дней и заполнения пропусков из имеющихся значений.

### 4. Трекер месяца (month-progress)

- **Эндпоинт:** `GET /api/forecast/{metric}/month-progress?year=...&month=...`.
- Считает «накопленный факт к сегодняшнему дню» и «ожидалось к этому дню» по выбранному месяцу.
- **Факт на сегодня:** сумма фактических значений (из Java) за все дни месяца до последней даты с данными включительно. «Прошедшие дни» определяются по фактам за этот месяц (если есть) или по концу истории метрики.
- **Ожидалось к этому дню:**  
  - если в сохранённом дневном прогнозе есть дни этого месяца — сумма прогнозных значений по этим дням за прошедший период;  
  - если дневного прогноза по этому месяцу нет — равномерное распределение месячного итога: `(прогноз на месяц / число дней месяца) × прошедшие дни`.
- **Отклонение:** факт минус ожидалось; темп (on_track / ahead / behind) по порогу 5%.
- **Пересчитанный итог месяца:** факт за прошедшие дни + прогноз на оставшиеся дни (из дневного прогноза или из того же равномерного распределения).

### 5. Сравнение с фактом (vs-actual) и точность (accuracy)

- **vs-actual:** за последние N дней сравниваются сохранённый прогноз и факт (данные из Java), отдаётся по дням: факт, прогноз, ошибка.
- **accuracy:** оценка качества последнего прогноза (MAPE/SMAPE и т.д.) по доступной истории.
- **monthly-accuracy:** история месячной точности из реестра (SMAPE/MAE по закрытым месяцам).
- **monthly-monitoring (POST):** после закрытия месяца считается фактический итог, сравнивается с сохранённым прогнозом месяца, результат пишется в реестр (для истории точности).

### 6. Экспорт в Excel

- **Эндпоинт:** `GET /api/forecast/export?date_from=...&date_to=...` (и опционально год/месяц).
- Собираются срезы метрик, факты, прогнозы, месячные роллапы в датасеты и упаковываются в xlsx.

### 7. Остальное

- **Leaderboard:** таблица лучших запусков по метрике (из локального реестра бэктестов).
- **Validation / registry-validate:** проверка целостности реестра и конфигов.
- **hierarchical-validate:** проверка иерархического прогноза (при включённой опции).

## Модели и ограничения

- **Минимум истории:** 90 дней для обычных моделей; для two_stage и hierarchical — больше (120 и т.д.).
- **Горизонт по умолчанию в бэкенде:** 31 день (`config.DEFAULT_HORIZON_DAYS`). На фронте в вызовах API по умолчанию передаётся `horizon=14`, поэтому сохраняемый прогноз часто оказывается на 14 дней от конца данных — и для «далёких» месяцев в файле нет дневных значений, трекер тогда использует равномерное распределение месячного итога для «ожидалось к этому дню».
- **Защиты:** ограничение взрывного роста прогноза (explosion guard), клипирование (например, utilization 0–100%, cancel_rate в [0,1]).
- **Праздники/события:** опционально используются в Prophet и в регрессорах SARIMAX (страна из конфига, без дополнительных источников событий из БД).

---

## Конфиг (config.py)

- `JAVA_BACKEND_URL` — адрес Java API.
- `METRICS` — список метрик.
- `MIN_HISTORY_DAYS`, `DEFAULT_HORIZON_DAYS`, `RETRAIN_INTERVAL_DAYS`.
- Пороги селектора (MAPE cap, margin для победы над базовой моделью).
- Включение/настройка two_stage, ensemble, hierarchical, провайдеров праздников.

---

## Итог одной фразой

Forecast-модуль **обучает на истории выручки и бронирований из Java**, выбирает модель по бэктесту, строит **дневные и месячные прогнозы**, сохраняет их в файлы и отдаёт через API; **трекер месяца** сравнивает накопленный факт с «ожидалось к этому дню» (по дневному прогнозу или по равномерному распределению месячного итога) и считает отклонение и пересчитанный итог месяца.
