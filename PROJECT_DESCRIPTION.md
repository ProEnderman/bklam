# Полное описание проекта Restaurant Management System

## ⚠️ Важные замечания о текущей реализации

Данный документ описывает как текущую реализацию, так и рекомендуемые улучшения для продакшена:

1. **Verification Codes:** В текущей реализации коды хранятся в открытом виде. Для продакшена рекомендуется хранить хеш кода (code_hash) с использованием bcrypt.

2. **Аутентификация:** Текущая реализация использует упрощенный подход с повторной проверкой пароля в verify. Рекомендуется использовать challenge-based подход без повторной передачи пароля.

3. **Platform Endpoints:** Эндпоинты для управления ресторанами и пользователями (HEAD_ADMIN) не реализованы, но описаны как необходимые.

4. **Управление пользователями:** API для ADMIN по управлению работниками ресторана не реализовано, но описано как необходимое.

5. **Конкурентность склада:** Защита от параллельных обновлений остатков не реализована. Рекомендуется добавить Optimistic Locking.

6. **CORS:** Текущая настройка использует `Allow-Origin: *` с `Allow-Credentials: true`, что небезопасно. Для продакшена требуется указать конкретный домен.

## Обзор системы

**Restaurant Management System** - это полнофункциональная система управления рестораном, построенная на Java Spring Boot (бэкенд) и React TypeScript (фронтенд). Система поддерживает мультитенантность (работа с несколькими ресторанами), имеет систему аутентификации с двухфакторной авторизацией через email, управление складом, заказами, аналитику и логирование активности.

## Архитектура базы данных

Система использует PostgreSQL с следующими основными таблицами:

### Основные сущности

1. **restaurants** - Рестораны
   - `id` (BIGSERIAL PRIMARY KEY)
   - `name` (VARCHAR, UNIQUE)
   - `created_at`, `updated_at` (TIMESTAMP)

2. **users** - Пользователи системы
   - `id` (BIGSERIAL PRIMARY KEY)
   - `username` (VARCHAR, UNIQUE) - используется как email
   - `password_hash` (VARCHAR) - bcrypt хеш пароля
   - `role` (VARCHAR) - роль: HEAD_ADMIN, ADMIN, REGULAR_WORKER
   - `restaurant_id` (BIGINT, FK) - привязка к ресторану (NULL для HEAD_ADMIN)
   - `first_name`, `last_name` (VARCHAR)
   - `is_active` (BOOLEAN)
   - `created_at`, `updated_at` (TIMESTAMP)

3. **ingredients** - Ингредиенты
   - `id` (BIGSERIAL PRIMARY KEY)
   - `name` (VARCHAR)
   - `unit` (VARCHAR) - единица измерения: G (граммы), ML (миллилитры), PCS (штуки)
   - `stock_qty` (NUMERIC) - текущий остаток (>= 0)
   - `min_qty` (NUMERIC) - минимальный остаток (>= 0)
   - `restaurant_id` (BIGINT, FK)
   - `created_at` (TIMESTAMP)
   - UNIQUE(name, restaurant_id)

4. **dishes** - Блюда
   - `id` (BIGSERIAL PRIMARY KEY)
   - `name` (VARCHAR)
   - `price` (NUMERIC, >= 0)
   - `is_active` (BOOLEAN) - soft delete
   - `restaurant_id` (BIGINT, FK)
   - `created_at` (TIMESTAMP)
   - UNIQUE(name, restaurant_id)

5. **dish_ingredients** - Рецепты блюд (связь многие-ко-многим)
   - `id` (BIGSERIAL PRIMARY KEY)
   - `dish_id` (BIGINT, FK)
   - `ingredient_id` (BIGINT, FK)
   - `qty_per_dish` (DOUBLE PRECISION, > 0)
   - UNIQUE(dish_id, ingredient_id)

6. **orders** - Заказы
   - `id` (BIGSERIAL PRIMARY KEY)
   - `status` (VARCHAR) - OPEN, CLOSED, CANCELED
   - `total_amount` (NUMERIC, >= 0)
   - `created_by` (VARCHAR) - username создателя
   - `restaurant_id` (BIGINT, FK)
   - `created_at`, `closed_at` (TIMESTAMP)

7. **order_items** - Позиции заказа
   - `id` (BIGSERIAL PRIMARY KEY)
   - `order_id` (BIGINT, FK)
   - `dish_id` (BIGINT, FK)
   - `qty` (INTEGER, > 0)
   - `price_at_time` (NUMERIC) - цена на момент заказа
   - `line_total` (NUMERIC) - qty * price_at_time

8. **stock_movements** - Движения по складу
   - `id` (BIGSERIAL PRIMARY KEY)
   - `ingredient_id` (BIGINT, FK)
   - `type` (VARCHAR) - IN (поступление), OUT (списание)
   - `qty` (NUMERIC, > 0)
   - `reason` (VARCHAR) - PURCHASE, SALE, SPOILAGE, EXPIRED, INVENTORY, OTHER
   - `order_id` (BIGINT, FK, NULL) - связь с заказом при списании по продаже
   - `created_by` (VARCHAR)
   - `created_at` (TIMESTAMP)
   - `note` (VARCHAR)

9. **refresh_tokens** - Refresh токены для JWT
   - `id` (BIGSERIAL PRIMARY KEY)
   - `user_id` (BIGINT, FK)
   - `token` (VARCHAR, UNIQUE)
   - `expires_at` (TIMESTAMP)
   - `revoked` (BOOLEAN)
   - `created_at` (TIMESTAMP)

10. **verification_codes** - Коды подтверждения для входа
    - `id` (BIGSERIAL PRIMARY KEY)
    - `user_id` (BIGINT, FK)
    - `challenge_id` (VARCHAR, UNIQUE) - уникальный идентификатор challenge для предотвращения повторных запросов
    - `code_hash` (VARCHAR) - **хеш кода** (bcrypt), НЕ сам код в открытом виде
    - `email` (VARCHAR)
    - `expires_at` (TIMESTAMP)
    - `used` (BOOLEAN)
    - `attempts_left` (INTEGER, DEFAULT 5) - количество оставшихся попыток ввода кода
    - `last_sent_at` (TIMESTAMP) - время последней отправки (анти-спам)
    - `send_count` (INTEGER, DEFAULT 1) - количество отправок кода
    - `created_at` (TIMESTAMP)
    
    **⚠️ ВАЖНО:** Код НЕ должен храниться в открытом виде. Только хеш кода (code_hash) для безопасности.

11. **activity_log** - Лог активности пользователей
    - `id` (BIGSERIAL PRIMARY KEY)
    - `action_type` (VARCHAR) - тип действия (CREATE, UPDATE, DELETE, CLOSE_ORDER и т.д.)
    - `entity_type` (VARCHAR) - тип сущности (ORDER, DISH, INGREDIENT и т.д.)
    - `entity_id` (BIGINT)
    - `user_name` (VARCHAR)
    - `description` (TEXT)
    - `old_values` (JSONB) - старое состояние
    - `new_values` (JSONB) - новое состояние
    - `created_at` (TIMESTAMP)

## Система ролей и прав доступа

### Роли пользователей

1. **HEAD_ADMIN** (Главный администратор)
   - Не привязан к конкретному ресторану (restaurant_id = NULL)
   - Может просматривать данные всех ресторанов
   - НЕ может создавать/редактировать заказы
   - НЕ может делать операции со складом
   - Используется для управления системой в целом

2. **ADMIN** (Администратор ресторана)
   - Привязан к конкретному ресторану
   - Полный доступ к данным своего ресторана:
     - Управление ингредиентами
     - Управление блюдами и рецептами
     - Управление складом (приход/списание)
     - Создание и управление заказами
     - Просмотр аналитики
     - Просмотр логов активности

3. **REGULAR_WORKER** (Обычный работник)
   - Привязан к конкретному ресторану
   - Ограниченный доступ:
     - Просмотр ингредиентов и блюд
     - Создание и редактирование ТОЛЬКО СВОИХ заказов
     - Закрытие ТОЛЬКО СВОИХ заказов
     - НЕ может управлять складом
     - НЕ может редактировать чужие заказы

### Механизм изоляции данных

- Все операции фильтруются по `restaurant_id` текущего пользователя
- HEAD_ADMIN видит все данные (restaurant_id = NULL в запросах)
- ADMIN и REGULAR_WORKER видят только данные своего ресторана
- Проверка прав доступа выполняется на уровне сервисов

## Система аутентификации

### Двухфакторная аутентификация через email

Процесс входа в систему:

1. **Запрос кода подтверждения** (`POST /api/auth/login/request-code`)
   - Пользователь отправляет email и пароль
   - Система проверяет учетные данные через Spring Security
   - Создается уникальный `challenge_id` (UUID)
   - Генерируется 6-значный код
   - **Код хешируется** (bcrypt) и сохраняется как `code_hash` в БД
   - Сохраняются: `challenge_id`, `code_hash`, `attempts_left=5`, `last_sent_at`, `send_count`
   - Код отправляется на email через SMTP2GO
   - Возвращается `challenge_id` клиенту
   - **Анти-спам:** Проверка `last_sent_at` - не чаще 1 раза в минуту

2. **Вход с кодом** (`POST /api/auth/login/verify`)
   - **Правильный подход:** Пользователь отправляет `challenge_id` и `code` (БЕЗ повторной передачи пароля)
   - Система находит challenge по `challenge_id`
   - Проверяется, что challenge не истек и не использован
   - Проверяется `attempts_left > 0`
   - Код хешируется и сравнивается с `code_hash` в БД
   - При неверном коде: `attempts_left` уменьшается
   - При успешной проверке:
     - Генерируются JWT токены:
       - **Access Token** - живет 15 минут, хранится в cookie `access_token`
       - **Refresh Token** - живет 30 дней, хранится в cookie `refresh_token`
     - Refresh token сохраняется в БД
     - Challenge помечается как использованный
     - Возвращается информация о пользователе
   
   **⚠️ Текущая реализация:** В коде есть упрощенный вариант с повторной проверкой пароля в verify. Для продакшена рекомендуется использовать подход с challenge_id без повторной передачи пароля.

3. **Обновление токена** (`POST /api/auth/refresh`)
   - Используется refresh token из cookie
   - Генерируется новый access token
   - Refresh token ротируется (старый удаляется, создается новый)

4. **Выход** (`POST /api/auth/logout`)
   - Все refresh токены пользователя помечаются как revoked
   - Удаляются cookies

### JWT токены

- Access token содержит: userId, username, role, restaurantId
- Токены подписываются секретным ключом (настраивается через JWT_SECRET)
- Используется алгоритм HS256

### Cookie параметры безопасности

**Access Token Cookie:**
- `HttpOnly=true` - защита от XSS (JavaScript не может получить доступ)
- `Secure=true` - **обязательно в продакшене** (передача только по HTTPS)
- `SameSite=Lax` - защита от CSRF (в продакшене можно использовать `Strict` если нет кросс-доменных сценариев)
- `Path=/` - доступен для всех путей
- `MaxAge=900` (15 минут)

**Refresh Token Cookie:**
- `HttpOnly=true` - защита от XSS
- `Secure=true` - **обязательно в продакшене**
- `SameSite=Lax` - защита от CSRF
- `Path=/api/auth/refresh` - доступен только для эндпоинта обновления токена
- `MaxAge=2592000` (30 дней)

**⚠️ ВАЖНО:** В текущей реализации `Secure=false` для локальной разработки. В продакшене ОБЯЗАТЕЛЬНО установить `Secure=true`.

## Основной функционал системы

### 1. Управление ингредиентами

**API эндпоинты:**
- `GET /api/ingredients` - список ингредиентов (с пагинацией, поиском, фильтром по минимуму)
- `POST /api/ingredients` - создание ингредиента
- `GET /api/ingredients/{id}` - получение ингредиента
- `PUT /api/ingredients/{id}` - обновление ингредиента
- `DELETE /api/ingredients/{id}` - удаление ингредиента
- `GET /api/ingredients/below-minimum` - ингредиенты ниже минимального остатка

**Поля ингредиента:**
- Название (уникально в рамках ресторана)
- Единица измерения (G, ML, PCS)
- Текущий остаток (>= 0)
- Минимальный остаток (>= 0)

**Бизнес-правила:**
- Остатки не могут быть отрицательными
- Уникальность названия проверяется в рамках ресторана

### 2. Управление блюдами

**API эндпоинты:**
- `GET /api/dishes` - список блюд (с пагинацией, поиском, фильтром по активности)
- `POST /api/dishes` - создание блюда
- `GET /api/dishes/{id}` - получение блюда
- `PUT /api/dishes/{id}` - обновление блюда
- `DELETE /api/dishes/{id}` - мягкое удаление (is_active = false)
- `GET /api/dishes/{id}/recipe` - получение рецепта блюда
- `PUT /api/dishes/{id}/recipe` - обновление рецепта блюда

**Поля блюда:**
- Название (уникально в рамках ресторана)
- Цена (>= 0)
- Активность (is_active)

**Рецепт блюда:**
- Список ингредиентов с количеством на порцию
- Каждый ингредиент: ingredientId, qtyPerDish
- При закрытии заказа автоматически вычисляется расход ингредиентов

**Бизнес-правила:**
- Нельзя закрыть заказ, если у блюда нет рецепта
- Цена должна быть >= 0
- Нельзя добавить неактивное блюдо в заказ

### 3. Управление складом

**API эндпоинты:**
- `POST /api/stock/in` - поступление товара (только ADMIN)
- `POST /api/stock/out` - списание товара (только ADMIN)
- `GET /api/stock/movements` - история движений (с фильтрами)
- `GET /api/stock/inventory` - текущие остатки (с фильтрами)

**Типы движений:**
- **IN** (поступление)
  - Причина: PURCHASE (закупка)
  
- **OUT** (списание)
  - Причины:
    - SALE - автоматическое списание при закрытии заказа
    - SPOILAGE - порча
    - EXPIRED - просрочка
    - INVENTORY - инвентаризация
    - OTHER - прочее

**Бизнес-правила:**
- Только ADMIN может делать приход/списание вручную
- Нельзя списать больше, чем есть на складе
- Остатки не могут быть отрицательными
- Все операции выполняются в транзакциях
- При списании по заказу (SALE) автоматически связывается с order_id

### 4. Управление заказами

**API эндпоинты:**
- `GET /api/orders` - список заказов (с фильтрами по статусу, датам, пагинацией)
- `POST /api/orders` - создание нового заказа (HEAD_ADMIN не может)
- `GET /api/orders/{id}` - получение заказа
- `POST /api/orders/{id}/items` - добавление позиции в заказ
- `PUT /api/orders/{id}/items/{itemId}` - обновление количества позиции
- `DELETE /api/orders/{id}/items/{itemId}` - удаление позиции
- `POST /api/orders/{id}/close` - закрытие заказа (продажа + списание ингредиентов)

**Статусы заказа:**
- **OPEN** - открыт, можно редактировать
- **CLOSED** - закрыт, ингредиенты списаны
- **CANCELED** - отменен

**Процесс работы с заказом:**

1. **Создание заказа**
   - Создается заказ со статусом OPEN
   - Заказ привязывается к ресторану и пользователю (created_by)

2. **Добавление позиций**
   - Добавляются блюда с количеством
   - Сохраняется цена на момент добавления (price_at_time)
   - Если блюдо уже есть в заказе, увеличивается количество
   - Пересчитывается общая сумма (total_amount)

3. **Редактирование заказа**
   - Можно изменять количество позиций
   - Можно удалять позиции
   - Можно только для OPEN заказов
   - REGULAR_WORKER может редактировать только свои заказы

4. **Закрытие заказа**
   - Проверяется, что у всех блюд есть рецепты
   - Вычисляется расход ингредиентов для всех позиций
   - Проверяется наличие достаточного количества ингредиентов на складе
   - Создаются движения по складу (OUT, SALE) для каждого ингредиента
   - Обновляются остатки ингредиентов
   - Заказ переводится в статус CLOSED
   - Устанавливается closed_at

5. **Отмена заказа**
   - Заказ переводится в статус CANCELED
   - Ингредиенты НЕ списываются

**Бизнес-правила:**
- Нельзя закрыть заказ без позиций
- Нельзя закрыть заказ, если у блюда нет рецепта
- Нельзя закрыть заказ, если недостаточно ингредиентов
- Нельзя редактировать закрытый/отмененный заказ
- REGULAR_WORKER может работать только со своими заказами
- HEAD_ADMIN не может создавать заказы

### 5. Аналитика

**API эндпоинты:**
- `GET /api/analytics/revenue` - общая выручка за период
- `GET /api/analytics/revenue/by-day` - выручка по дням
- `GET /api/analytics/top-dishes` - топ блюд по продажам (с лимитом)
- `GET /api/analytics/ingredient-usage` - расход ингредиентов за период
- `GET /api/analytics/problem-ingredients` - проблемные ингредиенты

**Проблемные ингредиенты:**
- Ингредиенты с остатком ниже минимума (LOW_STOCK)
- Ингредиенты с частым списанием по порче (HIGH_SPOILAGE)
- Ингредиенты с частым списанием по просрочке (HIGH_EXPIRED)

**Метрики:**
- Выручка считается по закрытым заказам (status = CLOSED)
- Топ блюд - по количеству проданных порций
- Расход ингредиентов - по движениям со reason = SALE

### 6. Platform Endpoints (для HEAD_ADMIN)

**⚠️ Текущее состояние:** Эти эндпоинты не реализованы в коде, но необходимы для полноценной работы системы.

**API эндпоинты:**
- `GET /api/platform/restaurants` - список всех ресторанов
- `POST /api/platform/restaurants` - создание нового ресторана
- `GET /api/platform/restaurants/{id}` - информация о ресторане
- `PUT /api/platform/restaurants/{id}` - обновление ресторана
- `DELETE /api/platform/restaurants/{id}` - удаление ресторана (мягкое)
- `POST /api/platform/restaurants/{id}/admins` - создание/назначение ADMIN для ресторана
- `GET /api/platform/users` - список всех пользователей (с фильтрацией по ресторану)
- `PATCH /api/platform/users/{id}/role` - изменение роли пользователя (выдача/отзыв ADMIN, назначение HEAD_ADMIN)

**Бизнес-правила:**
- Доступны только для HEAD_ADMIN
- HEAD_ADMIN может создавать рестораны
- HEAD_ADMIN может назначать ADMIN для ресторанов
- HEAD_ADMIN может изменять роли пользователей
- HEAD_ADMIN не может создавать заказы или управлять складом ресторанов

### 7. Управление пользователями (для ADMIN)

**⚠️ Текущее состояние:** Эти эндпоинты не реализованы в коде, но необходимы для полноценной работы системы.

**API эндпоинты:**
- `GET /api/users` - список работников ресторана (только своего ресторана)

## Безопасность

### Механизмы безопасности

1. **JWT аутентификация**
   - Access token в HttpOnly cookie
   - Refresh token в HttpOnly cookie
   - Токены подписываются секретным ключом

2. **Двухфакторная аутентификация**
   - Код подтверждения через email
   - Код живет 10 минут
   - Код одноразовый
   - **⚠️ ВАЖНО:** Код должен храниться как хеш (code_hash), а не в открытом виде
   - Ограничение попыток ввода (attempts_left)
   - Защита от спама (last_sent_at, send_count)

3. **Rate Limiting**
   - Ограничение 100 запросов в минуту на IP+User-Agent
   - Защита от DDoS

4. **CORS**
   - **Текущая настройка (разработка):**
     - `Access-Control-Allow-Credentials: true` - разрешена передача cookies
     - `Access-Control-Allow-Origin: *` - разрешены все домены (⚠️ небезопасно с credentials)
   - **⚠️ ПРОБЛЕМА:** Нельзя использовать `Allow-Origin: *` вместе с `Allow-Credentials: true`
   - **Правильная настройка для продакшена:**
     - `Access-Control-Allow-Credentials: true`
     - `Access-Control-Allow-Origin: https://your-frontend-domain.com` - **конкретный домен**, не `*`
     - `Access-Control-Allow-Headers: Origin, Content-Type, Accept, Authorization`
     - `Access-Control-Allow-Methods: GET, POST, PUT, DELETE, OPTIONS`
   - **Причина:** Браузеры блокируют запросы с credentials, если `Allow-Origin: *`

5. **Валидация данных**
   - Jakarta Bean Validation на уровне DTO
   - Проверка бизнес-правил на уровне сервисов

6. **Хеширование паролей**
   - BCrypt с силой 10
   - Пароли никогда не хранятся в открытом виде

7. **Изоляция данных**
   - Все запросы фильтруются по restaurant_id
   - Проверка прав доступа на уровне сервисов

### Исключения и обработка ошибок

- Глобальный обработчик исключений (GlobalExceptionHandler)
- Типизированные исключения:
  - `ResourceNotFoundException` (404)

## Особенности реализации

### Транзакции
- Все операции со складом выполняются в транзакциях
- Закрытие заказа - одна транзакция (списание ингредиентов + обновление заказа)
- Логирование в отдельной транзакции (не прерывает основную операцию)

### Конкурентность и целостность склада

**⚠️ КРИТИЧЕСКАЯ ПРОБЛЕМА:** При параллельном закрытии нескольких заказов одновременно склад может уйти в минус, даже при использовании транзакций.

**Проблема:**
- Два заказа закрываются одновременно
- Оба читают текущий остаток (например, 100)
- Оба проверяют достаточность (100 >= 50 и 100 >= 60)
- Оба списывают (100 - 50 = 50 и 100 - 60 = 40)
- Результат: остаток становится отрицательным или неверным

**Решения:**

**Вариант 1: Optimistic Locking (Рекомендуется)**
- Добавить в таблицу `ingredients` поле `version` (INTEGER, DEFAULT 0)
- Использовать JPA `@Version` аннотацию
- При обновлении остатка проверять версию
- При конфликте версии (другой процесс уже обновил) - повторить операцию или вернуть ошибку
- Преимущества: высокая производительность, нет блокировок
- Недостатки: нужна обработка конфликтов

**Вариант 2: Pessimistic Locking**
- Использовать `SELECT ... FOR UPDATE` при чтении ингредиента
- Блокировать строку на время транзакции
- Другие транзакции ждут разблокировки
- Преимущества: гарантированная целостность
- Недостатки: возможны блокировки и снижение производительности

**Вариант 3: Database Constraints + Retry**
- Использовать CHECK constraint: `stock_qty >= 0`
- При нарушении constraint - откатить транзакцию и повторить
- Преимущества: простота реализации
- Недостатки: возможны множественные повторы

**⚠️ Текущее состояние:** В коде не реализована защита от конкурентных обновлений. При параллельных закрытиях заказов возможны проблемы с целостностью данных. Рекомендуется реализовать Optimistic Locking.

### Мягкое удаление
- Блюда удаляются через is_active = false
- Удаленные блюда не отображаются в списках и не могут быть добавлены в заказы

### Изоляция данных (Multi-tenancy)

**Общие правила доступа:**

1. **Все таблицы данных ресторана имеют `restaurant_id`:**
   - `ingredients`, `dishes`, `orders`, `order_items`, `stock_movements` - все привязаны к ресторану
   - `users` - привязаны к ресторану (кроме HEAD_ADMIN)

2. **Автоматическая фильтрация по `restaurant_id`:**
   - Любой запрос от `ADMIN` или `REGULAR_WORKER` автоматически ограничивается их `restaurant_id`
   - Все репозитории и сервисы проверяют `restaurant_id` текущего пользователя
   - Метод `SecurityUtils.getCurrentRestaurantId()` возвращает `restaurant_id` из JWT токена

3. **HEAD_ADMIN - платформенные операции:**
   - `HEAD_ADMIN` имеет `restaurant_id = NULL`
   - Работает только с **platform endpoints** (управление ресторанами, пользователями)
   - **НЕ может** создавать/редактировать заказы, управлять складом ресторанов
   - Видит все данные всех ресторанов только для просмотра/аналитики

4. **Проверка прав доступа:**
   - Проверка выполняется на уровне сервисов через `SecurityUtils`
   - Перед каждой операцией проверяется соответствие `restaurant_id`
   - При попытке доступа к данным другого ресторана выбрасывается `BusinessException("Access denied")`

**Platform Endpoints (для HEAD_ADMIN):**

Следующие эндпоинты должны быть реализованы для полноценного управления платформой:

- `POST /api/platform/restaurants` - создание нового ресторана
- `GET /api/platform/restaurants` - список всех ресторанов
- `GET /api/platform/restaurants/{id}` - информация о ресторане
- `PUT /api/platform/restaurants/{id}` - обновление ресторана
- `POST /api/platform/restaurants/{id}/admins` - создание/назначение ADMIN для ресторана
- `PATCH /api/platform/users/{id}/role` - изменение роли пользователя (выдача/отзыв ADMIN)
- `GET /api/platform/users` - список всех пользователей (с фильтрацией по ресторану)

**⚠️ Текущее состояние:** Platform endpoints не реализованы в коде. Описаны как необходимые для полноценной работы системы.

### Логирование активности
- Все важные действия логируются
- Сохраняются старые и новые значения в JSONB
- Логирование не прерывает основную операцию
